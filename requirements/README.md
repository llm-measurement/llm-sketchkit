# Python Dependency Locks

The CI, fuzz, and release workflows install remote packages with
`--require-hashes --only-binary=:all:`. Each lock includes direct and transitive
dependencies. Source-only dependencies fail instead of fetching build tools.
Local checkouts and archives use `--no-index --no-deps --no-build-isolation`
after their dependencies are installed. Distribution builds use `--no-isolation`.

| Input and lock | Use |
|---|---|
| `runtime.in`, `runtime.txt` | Local package, wheel, and differential checks |
| `dev.in`, `dev.txt` | Tests, lint, types, and dependency audit on Python 3.11-3.14 |
| `notebook.in`, `notebook.txt` | Notebook execution and audit on Python 3.11 |
| `proto.in`, `proto.txt` | Protobuf generation on Python 3.11 |
| `release.in`, `release.txt` | Distribution builds and checks on Python 3.11 |
| `lock.in`, `lock.txt` | The lock generator |

The protobuf compiler has a separate environment and protobuf version.
The universal locks retain Python and platform markers. Hashes are generated by
uv from PyPI distribution metadata and checked by pip when downloading packages.
Hashes identify approved files; they do not prove that a package is safe.

## Updates

From the repository root, create a dedicated environment:

```sh
python3.11 -m venv .tools/python-locks
.tools/python-locks/bin/python -m pip install --require-hashes --only-binary=:all: -r requirements/lock.txt
PATH="$PWD/.tools/python-locks/bin:$PATH" bash scripts/update_python_locks.sh
```

Edit the `.in` files to change direct requirements. Keep packaging tools and
package requirements consistent with `pyproject.toml`. Pass `--upgrade` to the
script to update all allowed versions, or `--upgrade-package NAME` for one
package. Without those options, uv prefers the existing pins. To update uv,
change `lock.in`, regenerate with the existing locked generator, install the new
`lock.txt`, and regenerate again. Do not edit hashes by hand.

Review version, marker, and hash changes. Test fresh installations on Python
3.11-3.14, then run pytest, Ruff, Mypy, notebook execution, protobuf generation,
and the distribution checks from CI. Run the lock policy tests with:

```sh
python -m pytest -q .github/tests/test_python_locks.py
```

## Older Release Tags

The release workflow first checks out `github.workflow_sha`, the immutable commit
that contains the running workflow, and installs its release lock. It then checks
out the requested release tag and builds that source without isolation. An older
tag does not need to contain the lockfiles. No moving branch supplies build tools.
If the tag requires a different build backend version, the build fails without
fetching replacements. Review and hash-lock compatible tools before retrying.
To use this behavior for an older tag, dispatch the updated workflow and select
the old tag in `release_tag`; dispatching an old workflow does not update it.
